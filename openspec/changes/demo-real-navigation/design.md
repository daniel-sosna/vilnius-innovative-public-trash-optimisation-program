# Design

Use the existing pure plan_routes solver per carrier. Read bin capacities and eligible trucks with landfill coordinates in one short snapshot; close the database session before solving. Aggregate selected due-bin loads per (carrier, site), using collection_plan.FILL_SHARES. Pass the prediction levels explicitly; do not repeat inference or read a different saved collection plan.

Retain up to 150 eligible trucks across the run, selected in carrier round-robin order with stable truck-ID ordering so one carrier cannot consume every slot. Solve with seed 0, 1000 iterations and at most 180 seconds per carrier within a shared fourteen-minute navigation deadline. Translate each optimized truck's trips into a single route with landfill returns between trips. OSRM resolves each trip's ordered depot/stop/depot points; never replace failed road geometry with straight lines. The displayed stop list contains service stops only.

Return source pyvrp-osrm, routes and unserved stop/bin identities with Lithuanian reasons. The frontend checks that assigned plus unserved bins form an exact, disjoint partition of its prediction input. Show the unserved-bin count and reasons; show the truck table shell immediately after prediction, with its loading row covering marker appearance and navigation, then populate the five-row pages without a route drawing stage. If every bin is unserved, complete with an empty route result and explicit feedback. Navigation returns continuous OSRM legs tagged with service-stop indices; landfill-return legs have no service-stop index. Cache the last three completed runs for one hour in one backend worker. Tracking queries the cache by run ID and truck ID, reusing the same geometry and never a fixture. Refresh works while the run remains cached; missing/expired runs request a new plan. Collection coloring counts service legs only.

Use /admin/routes for the planning page and /admin/routes/truck/:truck_id?run_id=... for tracking. Redirect /admin/demo to the planning page, remove the separate RoutesPage registration and keep the shared project-date provider. Prediction markers and the map remain visible during planning and in completed results. Prediction feedback stays above the map; the navigation spinner lives inside the truck table below the map and is replaced by assigned rows, empty-result feedback or failure feedback. The incoming pyvrp dependency is already merged. Do not alter operational collection records or saved route plans.

Load PyVRP only inside the optimizer invocation. Stored-plan API imports must not require the solver at API startup; absent solver dependencies produce a navigation-specific unavailable response. Rebuilding the backend installs the locked solver dependency.
