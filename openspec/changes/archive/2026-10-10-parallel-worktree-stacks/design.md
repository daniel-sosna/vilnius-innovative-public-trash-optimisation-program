# Design

## Context

See proposal.md for the motivation. The current setup, as relevant here:

- **Ports:** `docker-compose.yml` publishes fixed host ports `5173:5173`, `8000:8000` and `5432:5432`.
- **Traffic inside the stack:** services reach each other by service name and container port (`http://backend:8000`, `db:5432`), so these never depend on host ports.
- **Per-checkout isolation:** Compose names the project after the checkout folder. Each worktree therefore already gets its own containers, network and volumes. For example, `docker volume ls` shows `aggregate-data-for-generator_postgres_data` next to `bin-schedule_postgres_data`.
- **Data directory:** the backend container mounts `./backend:/app`, so the importers' default data directory `/app/data` is `backend/data/` on the host. `table_import/cli.py` and `bin_population/cli.py` compute their defaults from the file location (`parents[3] / "data"`).
- **Settings:** `Settings` reads the repository-root `.env` when run natively. Inside the container that path resolves to `/.env`, which does not exist, and Compose passes only the variables listed under `environment`.
- **Agent folders:** the folders under `.claude/`, `.agents/` and `.github/` are generated by OpenSpec. A scratch copy showed that `openspec update --force` (1.14.1) keeps skill folders it did not create.
- **Compose version:** v5.6.0 locally. `docker compose config` confirmed the port interpolation and `!override` behaviour described below.

## Goals / Non-Goals

**Goals:**
- Several checkouts' stacks can run at the same time, with nothing to choose by hand.
- Single-branch developers see no change.
- Every worktree can use one shared folder of exports.
- One maintained copy of each skill serves three agents.

**Non-Goals:**
- Stable URLs in worktree mode. Developers who want them set the port variables.
- Hostname routing or a reverse proxy.
- Automatic setup outside the agent skills. No setup script is added; the skills follow documented manual steps.
- Changing container-internal ports, the API, the database schema or the frontend proxy.
- Windows support for the `COMPOSE_FILE` flag.

## Decisions

### 1. Port variables in the base file; an `!override` file for worktree mode

`docker-compose.yml`:

```yaml
ports: ["${FRONTEND_PORT:-5173}:5173"]   # likewise BACKEND_PORT:-8000, DB_PORT:-5432
```

`docker-compose.worktree.yml`:

```yaml
services:
  frontend:
    ports: !override
      - "${FRONTEND_PORT:+${FRONTEND_PORT}:}5173"
  # backend 8000 and db 5432 alike
```

A worktree turns the mode on with this line in its `.env`:

```
COMPOSE_FILE=docker-compose.yml:docker-compose.worktree.yml
```

Compose reads `COMPOSE_FILE` from the project `.env` by itself, so plain `docker compose ...` commands pick up the mode. When a port variable is unset, the nested interpolation produces the bare container port, and Docker chooses a free host port. When it is set, it produces `<port>:<container port>`.

`!override` is required. Without it, Compose merges port lists, and the stack would still publish 5173. The tag needs Compose 2.24 or newer.

**Alternatives considered:**
- **Docker-chosen ports by default.** Rejected: single-branch developers would lose stable URLs.
- **Setting `*_PORT=0` for a random port.** Rejected: it needs three settings instead of one flag, and Docker's treatment of host port `0` was not verified at runtime.
- **A `VIPTOP_RANDOM_PORTS=1` flag.** Not possible, because Compose interpolation has no conditionals. It would need a wrapper script around every `docker compose` call.
- **A reverse proxy with per-branch hostnames.** Rejected: it adds a service.

### 2. Isolation stays with Compose's default project name

No `COMPOSE_PROJECT_NAME` is set. With sibling worktree folders named after branches, folder names are already unique, and Compose isolates containers, networks and volumes by project. The remaining hazard is a new worktree whose folder name matches an older one's, which leaves volumes holding another branch's database. The setup skill detects this and asks the developer what to do.

**Alternative:** generate a unique project name in `.env`. Rejected: it renames everything for existing worktrees and makes `docker volume ls` harder to read.

### 3. `scripts/dev-info.sh` is a host script

A container cannot see its host-published port, so neither the backend nor a Compose hook can report the URLs. The script must run from the checkout and use only the Docker CLI, with no `jq` or Python dependency:

| What it prints | Where it comes from |
|---|---|
| URLs and ports | `docker compose port <service> <container port>` |
| Project name | `docker compose ls` / `ps` |
| Database user and name, never the password | the `db` container's environment, via `docker inspect --format` |
| Data directory | the backend container's `/app/data` mount source, via `docker inspect --format`, so it reports what is actually mounted |
| Mode (fixed or Docker-chosen) | whether `COMPOSE_FILE`, from the environment or `.env`, includes `docker-compose.worktree.yml` |

When a service is not running, the script says so and exits non-zero.

**Alternative:** a one-shot Compose service with the Docker socket mounted. Rejected for three reasons: the socket gives root-equivalent access, its path differs across rootless Docker, Docker Desktop and Podman, and its output is hidden behind `docker compose logs` after `up -d`.

### 4. `VIPTOP_DATA_DIR`: a Compose bind mount, also read natively

**Compose:** the backend gets this volume:

```yaml
- ${VIPTOP_DATA_DIR:-./backend/data}:/app/data
```

- It is nested inside the existing `./backend:/app` mount. When the variable is unset, this mounts `backend/data` onto itself, so nothing changes.
- Compose resolves relative paths from the project directory, which is the repository root.

**Never passed into the container:** the variable is not added to the backend's `environment`. Inside the container, the CLIs keep their `/app/data` default, which is the mounted folder.

**Native runs:** `Settings` gains an optional `viptop_data_dir` field, read from the environment or the root `.env`. A relative value is resolved from the repository root, matching Compose. Each CLI picks its default as follows:
1. `--dir` or `--file`, when given;
2. otherwise `VIPTOP_DATA_DIR`, when set;
3. otherwise `backend/data/`.

`bin_population` appends `population_density_1ha.geojson` to the chosen directory. The resolution lives in one small helper shared by both CLIs. A CLI that does not need the data directory is unaffected.

**Documentation:** `AGENTS.md` and the README's "For AI agents" note now say "the configured data directory (`VIPTOP_DATA_DIR`, default `backend/data/`)".

### 5. Skills: one maintained copy plus pointer files

```
.ai/skills/worktree-setup/SKILL.md      full instructions (maintained copy)
.ai/skills/worktree-create/SKILL.md

.claude/skills/worktree-*/SKILL.md      pointer files
.agents/skills/worktree-*/SKILL.md
.github/skills/worktree-*/SKILL.md
```

**Pointer files:** each repeats the maintained copy's `name` and `description` frontmatter, which agents use to decide when a skill applies. Its body says to read and follow `.ai/skills/<name>/SKILL.md`. This is the same indirection the repo already uses with `CLAUDE.md` → `@AGENTS.md`. `.ai/` is neutral ground that OpenSpec does not generate.

**Alternatives considered:**
- **Symlinks.** Rejected: they break on Windows checkouts without symlink support, and it is unknown whether every agent follows them.
- **Generated full copies kept in sync by a CI check.** Kept in reserve as the fallback if an agent does not follow the pointer file. It costs a sync script and a CI step.

### 6. Skill flow

**`worktree-create`:**
1. Read `git worktree list`.
2. If the non-bare worktrees share one parent folder, propose `<parent>/<branch with "/" replaced by "-">`. Otherwise ask where to put the worktree.
3. A new branch starts from `main`, after fetching, unless the developer names another base.
4. Run `git worktree add`, then follow `worktree-setup` inside the new folder.

**`worktree-setup`:**
1. Check that Docker is reachable.
2. Create `.env`:
   - Copy `.env.example`.
   - Append the `COMPOSE_FILE` line.
   - Append `VIPTOP_DATA_DIR`. When `../data/` holds the three exports, use `VIPTOP_DATA_DIR=../data` without asking. Otherwise ask the developer where the data folder is, and write that path.
   - An existing `.env` gets a shown diff and must be confirmed before any edit.
3. Check the exports. Confirm when a table has several exports.
4. Check for existing volumes, using `docker volume ls --filter label=com.docker.compose.project=<name>`.
5. Check that explicitly set ports are free.
6. Run `docker compose up --build -d`.
7. Wait until the backend answers. Startup runs migrations first.
8. Run `table_import` in the backend container.
9. Offer the refill commands for the derived tables the import reports emptying.
10. Run `scripts/dev-info.sh`.

The skills must never change Docker permissions, never run `bin_sync`, and never remove volumes or overwrite `.env` without explicit consent. specs/worktree-agent-skills lists the situations where they must ask the developer.

## Risks / Trade-offs

- **Vite live reload may assume host port 5173.** → An early task checks live reload on a non-5173 host port. If it fails, set `server.hmr.clientPort` from the page location (Vite's default behaviour) or document `FRONTEND_PORT`.
- **Docker-chosen ports change when a container is recreated.** Bookmarks and native `DATABASE_URL`s go stale. → `dev-info.sh` reprints them; developers who need stable values set the port variables.
- **If `VIPTOP_DATA_DIR` points at a missing folder, Docker creates an empty one,** possibly owned by root, and the import then reports "nothing to import". → The setup skill checks the folder before starting; the README warns about it.
- **An explicitly set port can later collide with a Docker-chosen one.** Docker picks from the ephemeral range, and explicit ports are usually low. → The skill checks explicit ports before `up`.
- **An agent may ignore a pointer file.** → An early task confirms that each agent lists and follows both skills. If one does not, switch to generated copies plus a CI check (Decision 5).
- **`COMPOSE_FILE` uses `:`, which is wrong on Windows.** → Accepted for this team. The README notes `COMPOSE_PATH_SEPARATOR`.
- **Leftover volumes from an earlier branch with the same folder name.** → The skill asks whether to reuse or remove them (Decision 2).

## Migration Plan

- **Single-branch checkouts:** no action is needed.
- **Existing worktrees:** to opt in, add the `COMPOSE_FILE` line and, optionally, `VIPTOP_DATA_DIR` to `.env`, then run `docker compose up -d`. The containers are recreated with new ports, and the volumes and data are kept.
- **Rollback:** remove those lines from `.env`. Reverting the change restores the fixed ports.
