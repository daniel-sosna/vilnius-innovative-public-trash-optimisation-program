# Tasks

Implementation follows [design.md](design.md) and the [collection-records](specs/collection-records/spec.md) and [bin-synchronization](specs/bin-synchronization/spec.md) contracts. Verification uses the running system, the shared one-shot synchronization command, and documented manual SQL/controlled-source procedures. Use disposable verification storage for synthetic records and failure exercises; do not seed operational service history.

## 1. Persistent collection records and migrations

- [x] 1.1 Add database settings and synchronous SQLAlchemy engine/session ownership using the existing psycopg driver, UTC sessions, and finite connection timeouts; add Alembic and update the backend lockfile. Verify `uv sync --locked`, database connectivity, and UTC session configuration against PostgreSQL.
- [x] 1.2 Define the five SQLAlchemy models with exactly the approved columns, external non-generated Bin IDs, independent generated internal IDs, required scalar/relationship values except nullable Bin address, named checks, restrictive foreign keys, route-stop position uniqueness, and the four justified relationship/history indexes. Verify model metadata matches the design table and has no extra domain fields or unsupported uniqueness rules.
- [x] 1.3 Create the Alembic environment and one initial upgrade/downgrade revision using the shared configuration and metadata. Verify `uv run alembic upgrade head` on an empty disposable database, repeat the command without data changes, and inspect PostgreSQL columns, identities, constraints, and indexes against the design; exercise downgrade/re-upgrade only on disposable storage.
- [x] 1.4 Document the raw collection-record contract and SQL inspection examples in README, including site-level capacity, service completion timestamps, observed fill categories, integer seconds, nullable addresses, ordered per-bin history, and truck attribution through Route. Verify documented SQL with explicitly synthetic temporary records: generated IDs, all five non-null/existence references, allowed values/ranges, duplicate stop positions, restrictive deletion, multiple trips on one date, timestamp offsets/ties, and route-to-truck joins; preserve no synthetic history in the normal database.
